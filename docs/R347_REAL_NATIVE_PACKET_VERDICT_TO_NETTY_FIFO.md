# R347 — Exact JNI per-packet source verdicts across client/Netty, FIFO and world fences

R346 verified a **native module-active tick candidate** can cross Java 8's client/Netty boundary using a primitive, generation-scoped one-slot mailbox. R347 is the next, materially harder boundary: a genuine **per-packet** Backtrack or Lag Range verdict from the native source event callbacks, not merely module activation.

## Implemented

- `SourcePacketVerdictBridge` is an owner-thread JNI producer and bounded synchronized primitive-only multi-entry FIFO. Its `begin(channelToken, actualJNIWorldTickReceipt)` authenticates both original native Backtrack and Lag Range event18 receipts, including their world/player/generation/tick, rejects a replayed tick or illegal same-generation channel/world change, and abandons old pending decisions on each new native tick.
- Every `observe(primitive SourcePacketReadOnlyQueue.Observation, now)` invokes the ACTUAL native Backtrack packet event2 for inbound packets or Lag Range packet event3 for outbound packets, with input fields constructed directly from that same immutable queue row. It validates resulting native receipt ownership and verdict domain. Backtrack reports `unchanged=0`, `hold=1`, `pass_feedback=2`; Lag Range reports `hold=1` or `pass=0`. The decision includes the source event, actual source opcode result, exact primitive packet sequence, channel/world/player/generation/tick, expiry, packet-kind/known-ID/position and original receipt timestamp. No actual `Packet` objects are retained.
- The foreign Netty reader can call only `consume(channel,world,generation,expectedSequence,now)`. It cannot invoke JNI, publish new decisions, or skip a queued earlier sequence: unexpected order, stale/future age or cap overflow fail the entire epoch closed instead of assigning a verdict to a DIFFERENT Packet. Hard cap is 64 verdicts and 100ms from packet observation and verdict publication; raw network packets continue to pass through the existing passive Forge tap.
- Critical timing limitation: the current passive R339 observer forwards the actual packet on Netty **before** the client thread can compute its native verdict. Therefore R347 deliberately does NOT attach the R344/R345 real packet owners in production, and its `hypotheticalHold` flag is **non-actionable**. Treating a delayed receipt as retrospective permission to withhold an already-forwarded packet would be incorrect.

## Tests

- `r347_java8_native_packet_verdict_netty_fifo` compiles Java 8 and runs the same native source JNI engine as the real player preview. Its controlled offline fixture explicitly sets Backtrack source reach eligibility (unlike the unproven live default); tests native Backtrack event2 genuine hold, target-status pass-feedback, native Lag Range event3 genuine hold on a closer movement packet, strict 1-2-3 source sequence mapping, read-only foreign Netty receipt consumption, wrong channel/world/generation rejection, publisher-thread gate, duplicate/mismatched sequence refusal, rollover into a fresh tick and then a new world, TTL poisoning, 65-result capacity overflow poisoning and explicit close/revoke.
- Existing R346 and earlier tests remain. ForgeGradle Minecraft 1.8.9 JDK8 assembles the primitive-only transport and requires its class in the JAR, but confirms no packet send/hold actions are present in the transport. The actual R344/R345 packet-owning Netty implementations remain only under `src/test/java`, explicitly excluded from distributed Forge JAR.

## Still missing for the original Slinky reconstruction

The original synchronous packet hook point (or a real bounded Netty-to-client admission handshake), event order and actual per-packet hold and release criteria, nonblocking expiration scheduling under channel lifetime, authentic source reach admission, native timing under in-world load, safe production packet owner integration and full GUI/gameplay parity. This project remains a draft read-only reconstruction experiment until those gaps are measured; no claimed complete 1:1 original Slinky functionality.
