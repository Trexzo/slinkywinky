# R340 — Native Timer Range packet event1 and real Netty traffic transparency tests

**Functional increment:** The native source bridge now exposes a tenth Java8 JNI opcode, `TIMER_RANGE_PACKET=9` with original source event `1`. It uses the *same* existing `ModuleExecutionBridge.bind_timer_range_source_packet` C++ controller state and emits one value-only `hold_packets` proposal. `SourceWorldReadOnlyHost.observePackets` invokes this opcode after the Lag Range event3 callback for each observed **outgoing** packet, and before the Inv Walk event23 callback for the three GUI packet types. No packet is actually held, delayed or cancelled. Diagnostic native receipt indicates what the source-inspired Timer Range policy would propose, not an original on-wire verdict.

The existing Java8/JNI smoke now checks that a genuine native Timer Range freeze-before source frame produces an event1 hold proposal. The real Netty source JNI replay smoke checks every outbound decoded observation causes both Lag Range event3 and Timer Range event1 callbacks with preserved FIFO chronology.

**First actual Netty handler execution tests:** `ForgeSourcePacketTap.diagnosticObserver` exposes only the existing passive `ChannelDuplexHandler` constructor to same-package Forge tests, never a gameplay sink. Four JUnit 4 tests under ForgeGradle Java8 run the handler inside Netty `EmbeddedChannel` with real Minecraft packet objects. These check: (1) inbound/outbound packet **reference identity** and untouched `ChannelPromise`, exactly-once delivery; (2) incoming S19 packet entity IDs never guessed by the network thread; (3) overflowing the bounded observer cannot stop or swallow a real packet; and (4) the C16 inventory-open packet remains intact and classified. The Forge workflow requires the four JUnit cases and refuses bundling test classes in the JAR.

**Limits:** This is a real Netty pipeline component test and a genuine JNI-controller diagnostic, not a live Minecraft process acceptance or proof of exact original Slinky networking logic. Netty callback order vs client-tick JNI replay differs from the original native source; held_ms remains deliberately zero because packets are already forwarded. There are no packet queues holding original objects or timer/key writes. PR #2 stays draft, PR #1 untouched; no recovered proprietary source committed.
