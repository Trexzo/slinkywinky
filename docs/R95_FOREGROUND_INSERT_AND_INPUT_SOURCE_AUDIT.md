## First-party input state and trust boundaries

- `include/slinkywinky/windows_insert_edge.hpp` defines a deterministic, native `VisibilityInsertEdge`. It never queries Windows or intercepts keystrokes itself. A **focused key-up** sample is required before the next rising Insert edge can toggle. Initial admission, focus loss, holding Insert while switching back into Minecraft, auto-repeated held samples, and an epoch reset cannot synthesize a toggle. A new focused release/repress is required after focus loss.
- `src/jni_bridge.cpp` uses this policy only after the existing source/callsite/owner-thread/WGL admission. The window must be the exact root of the current WGL device context, in the current game process, visible, non-minimized, and the **actual foreground window**. It polls `GetAsyncKeyState(VK_INSERT)` without installing keyboard hooks or injecting input into Minecraft.
- The JNI poll distinguishes external PID-scoped toggle events (`1`) from owner-focused Insert edges (`3`). R94's stop retains priority (`2`). Java `RendererWglEvidence` reconciles `toggles==keyToggles+eventToggles` before reporting a successful manual session. A separate `R95_INPUT_SOURCE_AUDIT keys=N events=M` line is emitted only during a restored original-JVM manual epoch; it is **not** a replacement for original SHA/JVM evidence and the existing R94 stop and renderer-release receipts.
- `tests/windows_r95_scoped_insert.py` is an *explicitly opted-in synthetic OS input acceptance helper*, **not physical hardware input**. It verifies the supervised exact original game PID and a unique, visible, unminimized window titled exactly `Minecraft 1.8.9`. It refuses to send keys unless that window is foreground. It checks the isolated sandbox `options.txt` for an explicit LWJGL `KEY_INSERT=210` binding collision, rejects an already-down Insert key, sends exactly two `SendInput` keydown/keyup pairs only with proven foreground, and guarantees a release for each issued down. It never sends keyboard input to another window. An unchanged sandbox options file is not proof that runtime/modded Minecraft keybindings cannot conflict.
- `--render-key-acceptance` uses the existing seven original-Mojang 1.8.9 stages and original-only `--render-visibility=manual` Attach mode. The key-specific checker demands **exactly** `keys=2 events=0`, two reconciled toggles, genuine on/off frames, source-pinned bytecode restored, and a verified `--stop-visibility` operator release. Any failure refuses a PASS; an admission failure requests a cooperative PID-scoped stop, without claiming successful restoration from the stop request alone.
- Existing R94 operator-event acceptance stays separate and unchanged. R95 does not enable input capture, module toggles, mouse handling, profiles, combat, networking or any gameplay behavior.
